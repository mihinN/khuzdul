- Alignment of Hot Code Path
    * this means we have to align instruction , collections of  32bytes 256bits (in x86 AVX-512 heavy codes are collections of 64bytes - 512bits)

    * this is important because think some branch instruction like loop, start 6bytes before the
    the cache line boundry. that means we can get that whole branch data into that cache , and
    cpu need to run two cycle to complete that one iteration. so we called this "Fetch Boundary Split"
    * so we have to wait and , add NOP to complete those 6bytes and start fresh next instruction
    start at multiple of 16

    Example:
        NOP              ; padding bytes added by assembler
        NOP              ; to push loop start forward
        ALIGN 16         ; next instruction starts at multiple of 16
    loop_start:
        add rax, rbx
        dec rcx
        jnz loop_start

- What Assembler should do ?
    * For your x86-64 assembler specifically, this means supporting an ALIGN directive that emits NOP padding bytes:
    Code :
    ALIGN 16    ; emits 0–15 NOP bytes to reach next 16-byte boundary
    ALIGN 32    ; emits 0–31 NOP bytes to reach next 32-byte boundary
- This is like converting into Chunks

    chunk 0:  [00–0F]  ← one fetch unit
    chunk 1:  [10–1F]  ← one fetch unit
    chunk 2:  [20–2F]  ← one fetch unit
    chunk 3:  [30–3F]  ← one fetch unit

- How Microcode update happends via interent 
    * i remember this process in early days fully. not now 
    * how ever this loads on ROM
    * Currently microcode updates are cryptographically signed by Intel/AMD. You need their private key to load custom microcode on production silicon.
    * check more about "eFuse"


eFuse region contains:
├── Public key hash (for microcode signature verification)
├── Decryption key (for encrypted microcode)
├── Secure Boot keys
├── Device unique ID
├── Feature enable/disable bits (artificial product differentiation)
└── Security version numbers (prevent rollback to old vulnerable microcode)

You were thinking:
    key in ROM → encrypted → hardware decrypts

Reality is very close:
    public key hash burned in eFuses (permanent, hardware)
         ↓
    microcode arrives encrypted + signed
         ↓
    hardware verification engine checks signature
    (dedicated circuit, key never exposed)
         ↓
    hardware decryption engine decrypts microcode
    (dedicated circuit, key never exposed)
         ↓
    microcode loaded into microcode RAM
         ↓
    CPU executes it
